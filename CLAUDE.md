# Southbound Coaching — Project Guide & Handoff

Southbound Coaching (formerly "EddieOS") is Eddie Steers' coaching business platform: a public marketing site for guests, plus an installable app (PWA) where clients train and Eddie coaches them. It covers online coaching, running and strength programming, and 1-on-1 or group soccer training.

- **Live site:** https://southboundcoaching.com (GitHub Pages custom domain via the `CNAME` file; deploys automatically from `main`). The old https://eddiesteers777.github.io/eddie-dashboard/ address redirects there. Absolute URLs (share tags, the COROS `oauth/client-metadata.json` client ID) use the domain; everything else uses relative paths, so keep it that way.
- **Repo:** `eddiesteers777/eddie-dashboard`
- **Deeper background:** `docs/PRODUCT_ARCHITECTURE.md` (the original audit, account/role design, and roadmap)

## The three experiences

| Who | What they see | How it's decided |
|---|---|---|
| **Guest** (signed out) | Public site only: Home, About, Packages, Contact, Get the App, Apply | `js/loadHeader.js` sends signed-out visitors on any app page to `home.html` |
| **Client** (approved, `status: "active"`) | The app, filtered to the services Eddie granted them: menus, pages, Today and My Progress | `services[]` on their profile → capabilities (`js/services.js`), applied by `js/navAccess.js` / `js/todayLayout.js` |
| **Coach / admin** (`isCoachApproved: true`) | Everything, plus the Coach section | Eddie's own account. Approved coaches can approve anyone. |

A new sign-in starts as a **pending client** with no services, so it sees only Today (a "waiting for approval" card), its profile and Get the App until approved. That's by design. A denied (archived) account sees "Your account isn't active".

## How it's built

- **Static site, no build step.** Plain HTML/CSS/ES-module JS, hosted on GitHub Pages. PWA via `manifest.json` + `sw.js` (see **Speed + offline** below). **Run `npm run manifest` after changing ANY file** (not just adding/removing): it rewrites the precache list in `sw.js` (a fingerprint per file), which is how installed phones learn about a new version; a static test fails when it's stale.
- **Firebase** (project `eddie-s-dashboard`): Google sign-in only (`js/auth.js`), Firestore for data (`js/firebase.js`). Firestore uses **single-tab persistent IndexedDB caching**; an additional Southbound tab falls back to memory so another tab cannot keep the persistent cache alive while an account transition clears it. SDK loads from `gstatic.com` (and is kept by the service worker). Signing out (`logout()` in `js/auth.js`, used by the header, More and Settings) clears that cache plus all account-sensitive local/session state, including synced app data, COROS OAuth credentials/history, Strava history, role/access caches, coach notes, offline email outbox, and cloud-sync bookkeeping. An account-owner sentinel (`sb-account-storage-owner`) and the centralized auth-transition guard detect UID changes, clear account state, and reload the page before the new account continues. On the first post-upgrade sign-in, when no owner marker exists, any ambiguous legacy account state is cleared once before the current account is established; synced data is then restored from that account's cloud copy. Cloud sync also resets its in-memory snapshot when the UID changes and aborts stale reads/writes/mirrors, so data from the prior account cannot be replayed after an auth transition. Device-only UI preferences are preserved.
- **Speed + offline (2026-09-28):** measured on a throttled phone (slow 4G + 4x CPU, `perf2.mjs`-style harness: a patched copy of the site served with gzip/ETag, one bandwidth budget shared by the page and the service worker, a throttling proxy in front of the Firestore emulator, real offline by dropping connections). What made it slow, and what changed:
  - **Cloud sync** re-sent everything every 30 s: each tick read the whole `users/{uid}/sync/localStorage` doc and wrote it back (plus the `sharedPlans` mirror) even with nothing changed: ~650 KB down + ~620 KB up a minute for Eddie's data, and every page load downloaded the whole doc (several pages twice: they call `initCloudSync()` too). Now (`js/cloudSync.js`): pushes only when a synced key changed (the last-synced copy is parsed once and kept in memory), the mirror only when a plan key changed; a tiny `users/{uid}/sync/meta` doc (`{ v }`, changed in the same transaction as every push, same owner-only rule) lets a page load read ~100 bytes and skip the big read when nothing changed (a full read still at least every 6 h, `__cloudSyncFullPullAt`, for devices on old code); `initCloudSync()` runs once per page whoever calls it; `pagehide` instead of `beforeunload` (keeps the back/forward cache); nothing is sent or read offline; status goes out as `sb:sync-status` events. Manual Sync buttons force a full read.
  - **The tab bar waited on Firestore** (profile read, twice): 2–9 s on a slow phone, ~10 s or never offline. Now `js/navAccess.js` remembers the last access on the device (`sb-nav-access`, device-only) and `js/loadHeader.js` draws the tab bar from it at once, redrawing only if the fresh profile differs; `getMyProfile()` is read once per page (`js/userProfile.js`, cleared after the account's own profile writes).
  - **Network-first service worker**: every page load waited on the network for the HTML, CSS and each module (and the Firebase SDK wasn't kept at all). Now `sw.js`: the whole app (every page, script, stylesheet, font, icon, logo, reaction drawing: `precacheFiles()` in `scripts/build-manifest.mjs`, ~260 files, ~1 MB over the wire once) is one VERSION served from the device (pages ignore `?query`); a deploy changes the list, the browser installs the new version in the background, copying unchanged files and fetching only changed ones (`cache: "no-cache"`), all or nothing; the page offers **"A new version of Southbound is available. Refresh"** (`js/netStatus.js`), and the next page anyone opens switches to it (`switchVersion` in `sw.js`: the old worker answers that navigation at once with a tiny `Refresh: 0` page and tells the new one to take over, so the reload is served by the new version; skipped while another Southbound tab is open; an open page only reloads on the person's own tap), so nobody is stuck; old versions are deleted on activation; the first install (or replacing the old worker) takes over at once. The SDK (versioned gstatic URLs) is cache-first; photos and jsDelivr/cdnjs libraries stale-while-revalidate (`sb-runtime` capped at 80, `sb-cdn`); Firestore, sign-in, COROS and all non-GET requests are never touched.
  - **Photos**: Home loaded ~890 KB of full-size JPEGs on a phone. Now `srcset` WebP copies (`scripts/build-images.py`: 480/800/1280 for the offer cards, 560/840/1120 for the hero, 500/1000 gallery; `sizes` aim at ~2x density on phones), `loading="lazy"` below the fold, `width`/`height`, `fetchpriority="high"` on the hero; the `.jpg` stays as the fallback. **After replacing a photo, run `python3 scripts/build-images.py`** (a static test compares each photo's fingerprint in `images/sizes.json`).
  - **Nutrition** loaded two barcode libraries from jsDelivr, render-blocking, on every visit, and the scanner code looked for a third library that was never loaded, so Scan always failed. `js/barcodeScanner.js` now uses the browser's `BarcodeDetector` (Android Chrome) or the zbar polyfill loaded on the first tap (iPhone), with its own camera `<video>`.
  - **Offline changes**: localStorage data was already a queue (changed keys push on `online`). Firestore writes that matter to clients (workout/strength logs, check-ins, change requests) go through `settleWrite()` in `js/offlineWrite.js`: offline or no answer within 8 s = "Saved on this phone. It'll sync when you're back online.", but only after a device-cache read of the same doc has finished (`storedOnDevice`: Firestore runs its work in order, so that means the write is stored on the phone) (the persistent cache keeps it across app restarts and sends it once; fixed doc IDs, and change requests now make their ID up front, so nothing duplicates); `sb:write-synced` / `sb:write-failed` toasts when the server answers. Emails asked for offline wait in a device-only outbox (`sb-email-outbox`, ≤20, 3 days) and go out on reconnect. **Conflicts**: the existing rules hold: per-key last write wins with unpushed local changes kept (cloud sync); a coach's new plan version never overwrites the client's done marks (`mergeRuntimeByDate`); workout logs are the client's own docs, separate from the prescription.
  - **The pill** (`js/netStatus.js`, `css/style.css` "CONNECTION / VERSION PILL", loaded by `js/registerSW.js` on every page that registers the worker): offline → "You're offline. Changes will sync when you're back online. Last synced …", shrinking to "Offline"; back online → "Back online. Syncing your changes…" → "Synced" (cloud push + Firestore `waitForPendingWrites`); new version → Refresh. The desktop sync pill says "Offline — last synced …" instead of "Sync error".
  - Public pages still don't register the worker (a visitor reading Home doesn't download the app); once someone has the app, the worker serves them too.

Weekly miles start at their current miles (0 = about 2 per run day), grow 7–10% a week by experience (at least 1, at most 4 miles), cut back ~20%, hold at the peak, and taper from the peak **actually reached** (1 week 55%; 2: 75/50%; 3: 80/65/45%); a final guard keeps any week within ~15% (or 4 miles) of the last two as laid out. The long run starts from their longest recent run (at least a quarter of current miles, up to 12) and grows 1 mi a week (1.5 marathon, 2 ultras) to the race's target (5K 8, 10K 10, half 13, marathon 20, 50K 22, 50 mile 26; training 30% of peak, 4–16), cut back 25% on cutbacks, shorter in taper, none in race week, and never more than its share of what the week can really hold (35–60% by run count, +5% for marathon/ultra; no share rule with 2 runs). Day layout: runs are sized around 3.5 miles, so a low week has fewer, real runs (none under 2 miles, 1.5 on weeks under 12); quality days only once a week has 12+ miles (2 at 20+, 3 at 30+), never side by side, off the day before the long run unless there's no other day (`spacedDays`); easy days share the rest up to 12 miles and below the long run; the day after the long run is recovery with 5+ runs; ultras get a back-to-back run next to the long run in Build / Race Specific / Peak; the day before the race is a ≤3-mile shakeout; brand-new runners on small weeks get run/walk sessions. Workouts that don't fit a short day lose reps, then get shorter reps. Plain warnings for the editor's "Worth a look": the peak isn't safely reachable in the time, too few run days for the miles (some weeks come in short), fewer weeks than the race usually takes, a peak below the race's norm, the long run falling short of the race's usual target, a new runner on run/walk. The old engines gave 0.5-mile runs, 96-mile jumps, 16-mile "easy" days on 4-day plans and three taper weeks in a six-week plan; a sweep of ~11,000 random settings now breaks none of the rules.

## Gotchas we've already hit (don't repeat them)

- **`data-requires` and `hidden` don't mix on one element.** The nav pass (`applyNavAccess`) sets `hidden` from the capability, so a section with `data-requires` that hides itself for "nothing to show" gets unhidden as an empty box (Today's Readiness card, 2026-10-03). Use its own class (`rd-none`) or leave `data-requires` off and let `js/todayLayout.js`'s `sb-off` handle the capability.
- **`[hidden]` vs CSS `display`:** any class that sets `display` beats the browser's native `[hidden]`. Every page/component scope has a blanket override (`.clients-page [hidden]{display:none!important}` etc.). Add one when writing new CSS.
- **Flex rows with wrapping text:** use `align-items:flex-start`, or action buttons float to the middle of tall rows.
- **Flex wrapping:** `flex:1` (basis 0) overrides `width:100%`. Use `flex:0 0 100%` to force an item onto its own row.
- **Reload loop:** comparing Firestore data with plain `JSON.stringify` caused an infinite reload (key order changes). Use `stableStringify` in `js/coachAccess.js`.
- **Guest redirect** only fires when Firebase definitively says "signed out". It never fires on an auth-load error, so offline users aren't kicked out.
- **Overlays** need `z-index` above the navbar (1000) and search overlay (4500). The plan editor uses 5000.
- **Cards with `overflow:hidden` inside a scrolling flex column shrink to slivers** (their flex min-height becomes 0). Give them `flex-shrink:0` -- this was the live-workout "things overlap" bug.
- **The domain move changed the origin.** Browser storage (localStorage, the installed app, COROS tokens) is per-origin, so it doesn't carry over from the github.io address; signed-in users get their data back from cloud sync on the new domain. Google sign-in only works on domains listed in Firebase Console → Authentication → Settings → Authorized domains.
- **Honeypot fields must not look like real fields.** The contact form's hidden spam trap was once labeled "Company"; browser autofill filled it, so real questions were silently dropped while showing "Question sent". Keep it as `sbLeaveEmpty` ("Leave this empty", `autocomplete="off"` + password-manager ignore attributes).
- **`Promise.all` with a long positional list breaks silently.** `loadClientRecord` gained a part without its name in the destructuring, every later value shifted by one, and the Client Hub said "client not found" for every client (2026-09-30 to 10-03). It now uses `allNamed({ name: promise })`; do the same for any list longer than three or four.
- **Hand-uploaded files can drop rules.** A 2026-09-17 upload replaced `css/nutrition.css` and silently removed the barcode-scanner modal, food log and confirm styles (restored 2026-09-25). If Eddie uploads a file, diff it against the previous version.
- **Phone inputs must be 16px+** or iOS zooms on focus. `css/style.css` forces 16px on form fields at <=900px (the big fueling-target and record inputs are excluded); small buttons get ~40px touch targets there too.
- **Reading your own not-yet-created doc is permission-denied, not "missing".** (A third time, 2026-10-05: `listMyWearableShares` threw on a client's first share, so the sharing switches never showed for a client who hadn't shared yet.) Rules like `checkins` check `resource.data.clientUid`, which fails when there's no doc. `submitCheckin` read first, so every first weekly check-in failed on the live site until 2026-09-25. Treat permission-denied on your own doc ID as "new", and test the real create path, not an admin-seeded doc. It happened again on 2026-10-03: `assignClient` (every Find a Client assignment, and the auto-link on Approve) and `saveWearableShare` (a client's first wearable share) read first; both now write without the pre-read.
- **Page CSS resets body padding on phones.** Several pages set `body{padding:20px}`, which wiped out the bottom tab bar's padding. `loadHeader` now adds `body.has-bottomnav`, padded with `!important` in `css/style.css`.
- **Phone overrides in `css/style.css` need `!important`.** Page stylesheets load after it, so equal-specificity rules there win (yesterday's first tap-target pass silently didn't apply).
- **Any rules change needs a test.** Add the attack and the legitimate flow to `tests/rules.test.mjs`.
- **Firestore rules stop at 1,000 checks per request** ("Unable to evaluate the expression as the maximum of 1000 expressions…" = permission-denied). Every item of a list literal counts (`hasOnly([...50 keys])` alone is ~100), and each call to a helper function costs far more than the same check written inline. For a big document, join values and match one pattern (`scripts/build-profile-rules.mjs`), and add a rules test that saves the fullest possible document. Inside a joined pattern `$` means the end of the whole string, not of one part.
- **A coached plan's source of truth is `coachingPlans`, not the client's device.** Never write a coach plan into `running-programs`/`training-programs` or edit it through `sharedPlans`; publish a new version. The device copy (`coach-plans`) is a cache plus the client's own records; completion/results never go into a published version (`stripRuntime`).
- **A client's copy and its versions hold only two weeks.** Anything coach-side that needs the whole plan (editing, the hub summary, totals) reads `coachingPlanMasters`, never a version or `sharedPlans.coachPlans` (those are for the client's done marks). Editing from a two-week version and publishing would delete the rest of the plan.
- **Firestore can't query a subcollection without a filter the rules can check.** Listing `versions` needs `where("coachUid"|"clientUid", "==", uid)` (`listVersions`).
- **`sbConfirm`/`sbPrompt` are async.** Swapping one in for `confirm()` means the enclosing function/listener must be `async` (and callers mustn't rely on a sync return). `node --check` catches a stray `await`.
- **`.sb-wait` placeholders shimmer until they have text.** If code can leave one empty on purpose, give it text or remove the class, or it shimmers forever.
- **The `.primary-btn`/`.coach-button` tan-to-blue gradient** (`#2D7FFF`, pre-rebrand) was still live until 2026-09-25. Search for gradients before assuming the palette is clean.

- **The global `.card` is Today's link card** (`css/style.css`: hover lift, "→", an absolute glow layer over the whole card). A page that names its own panels `.card` inherits all three, and the glow layer swallows taps on anything not positioned (the 75-Day page's edit button, until 2026-09-28). Use another class name, or switch them off as `75day.html` does.
- **Percentage padding is a share of the parent's width, not the element's.** The first brand tile used `padding:15%` and the padding swallowed the whole tile (the mark vanished). Size it from the element: `calc(var(--sb-tile) * .17)`.
- **The mobile top bar is a size container (`sbmtop`).** Its logo steps down with the bar's own width (smaller under 300px, the mark alone under 240px), so a narrow bar can't push the wordmark under the buttons. The public header shrinks its logo and Sign In under 400px for the same reason (they collided at 320px).
- **Every changed file needs `npm run manifest`.** The service worker serves the app from the phone and only re-downloads files whose fingerprint in `sw.js` changed; a hand-uploaded file without it would stay old on installed phones until the next proper deploy (CI fails meanwhile). Same for photos: `python3 scripts/build-images.py`.
- **`pkill -f <pattern>` kills your own shell** when the pattern appears in the command line (it did three times, 2026-09-27): stop test servers by PID.
- **Cloud sync timestamps a key only when it's pushed.** A pull used to overwrite anything changed on this device since the last push with the cloud's older copy, then reload the page. Pages that save as they go (the COROS history filling in a week at a time) reloaded over and over and lost what they'd saved (2026-09-27). `pullFromCloud` now keeps any key that differs from the last-synced snapshot (`__cloudSyncSnapshot`) and stamps it so the next push sends it. Changes from another device to keys untouched here still come in. **And the pull must not mark it synced** (2026-10-03): pushes only send keys that differ from the snapshot, so the pull's `markPulled(cloudData)` puts only what the cloud also holds into the snapshot; a kept key (or one the cloud doesn't have, e.g. a new account's first data) stays out of it until a push succeeds. Before this, a change made offline or right before closing the app stayed on that device whenever another device had synced in between.

## Testing

- `npm install` once, then `npm test` runs everything: `npm run test:static` (every script parses, every local link/asset/import exists, public pages have meta descriptions and no placeholder text, `site-manifest.json` is current) and `npm run test:rules` (the Firestore emulator against `firestore.rules`). GitHub Actions (`.github/workflows/ci.yml`) runs both on every push.

- The sandbox can't reach `gstatic.com`, so the real Firebase SDK won't load. Test with Playwright (installed globally at `/opt/node22/lib/node_modules/playwright`, browsers at `/opt/pw-browsers`) by serving the repo with `python3 -m http.server 8934` and mocking `js/auth.js`, `js/firebase.js`, `js/userProfile.js`, `js/cloudSync.js`, etc. via `page.route()`.
